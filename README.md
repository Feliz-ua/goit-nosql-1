# GoIT NoSQL — робота з даними Spotify

Коротко: проект завантажує набір даних треків Spotify у MongoDB та містить приклади запитів і трансформацій.

**Вміст**
- `scripts/01_load_data.py` — скрипт на Python для завантаження `dataset.csv` у колекцію `tracks_raw`.
- `scripts/02_transform.js` — трансформації/очистка в MongoDB (запуск через `mongosh`).
- `queries/` — приклади запитів на різні частини завдання (`part2_queries.js`, `part3_aggregations.js`, `part4_indexes.js`).

## Вимоги
- Python 3.8+
- `mongosh` (MongoDB Shell) для запуску JS-скриптів у MongoDB

Встановити Python-залежності:

```bash
python -m venv .venv
source .venv/bin/activate    # macOS / Linux
# Або для Windows PowerShell виконайте:
# .venv\Scripts\Activate.ps1
# або (якщо використовуєте cmd.exe):
# .venv\Scripts\activate.bat
pip install -r requirements.txt
```

## Налаштування з'єднання з MongoDB
Створіть файл `.env` або встановіть змінну оточення `MONGO_URI`, наприклад:

```
MONGO_URI=mongodb+srv://<user>:<password>@cluster0.mongodb.net/spotify
```

Альтернативно для запуску JS-скриптів можна передати URI безпосередньо в команді `mongosh`.

Використовуйте `.env.example` (додано до репозиторію). Скопіюйте його у `.env` і заповніть:

```bash
cp .env.example .env    # macOS / Linux
# У Windows PowerShell:
Copy-Item .env.example .env
```

## Додавання даних
1. Завантажте файл `dataset.csv` (файл ігнорується Git-ом).
2. Запустіть скрипт завантаження:

```bash
python scripts/01_load_data.py
```

3. За потреби застосуйте трансформації (через `mongosh`):

```bash
mongosh "${MONGO_URI}" --file scripts/02_transform.js
```

## Запуск запитів
Файли в папці `queries/` містять приклади запитів/агрегацій. Їх можна виконати через `mongosh`:

```bash
mongosh "${MONGO_URI}" --file queries/part3_aggregations.js
```

Або відкрийте код і запускайте потрібні запити вручну у вашому середовищі (Compass, mongosh REPL тощо).

## Структура репозиторію

**Відповіді на обов’язкові теоретичні питання**
***Частина 1***
1.  Чому аудіо-характеристики винесені в окремий об’єкт audio_features, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?
Це покращує читабельність та структуру документа. Вкладення вигідне, коли ми хочемо отримати або виключити всі аудіо-властивості одним полем у проєкції ({ audio_features: 1 }). Проблеми можуть виникнути, якщо нам потрібно часто індексувати дуже багато вкладених полів окремо або якщо глибина вкладеності стає занадто великою (ускладнюється синтаксис запитів).

2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?
Масиви дозволяють використовувати потужні оператори MongoDB (наприклад, $in, $all, $size) та створювати multi-key індекси. Запити типу "знайти всі треки конкретного артиста" стають миттєвими та не потребують використання повільних регулярних виразів для пошуку по рядку.

3. Що таке $out і чим він відрізняється від $merge? Коли використовувати кожен?
Оператор $out повністю перезаписує цільову колекцію (або створює нову), замінюючи всі існуючі дані. Оператор $merge дозволяє оновлювати існуючу колекцію (робити upsert), додаючи нові документи або змінюючи існуючі без видалення старих даних. $out використовується для повної ініціалізації, а $merge — для періодичних оновлень.

***Частина 2***
1. Для чого використовується інструкція $unwind?
Вона "розгортає" масив. Якщо документ містить масив із 3 елементів, $unwind створить 3 окремих документи, кожен з яких міститиме один елемент масиву. Це необхідно для групування ($group) або фільтрації за окремими елементами масиву.

2. Чим $stdDevPop відрізняється від $stdDevSamp?
$stdDevPop обчислює стандартне відхилення для генеральної сукупності (коли ми маємо доступ до всіх можливих даних, як у нашому датасеті). $stdDevSamp використовується для вибірки (коли дані є лише частиною більшої популяції).

***Частина 3***
1. У запиті 1 ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1? А що станеться, якщо вибирати виконавців із більш ніж 50 треками? Поясніть результат.
Якщо знизити поріг до 1, у топ потраплять "артисти одного хіта" (one-hit wonders) або маловідомі виконавці, чий єдиний трек випадково отримав високу популярність (100 балів). Це спотворить аналітику. Якщо підняти до 50, ми відсіємо нових або нішевих артистів, залишивши лише "ветеранів" індустрії з великою дискографією.

2. У запиті 3 ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50? Поясніть результат.
Якщо знизити поріг до 50, у результатах можуть опинитися дуже специфічні піджанри з малою вибіркою. Це статистично ненадійно, оскільки наявність лише кількох дуже танцювальних треків може підняти весь жанр у топ, хоча загалом він не є популярним для танців.

***Частина 4***

1. Пошук за точним збігом та діапазонний пошук. Що змінилося в плані виконання?
До створення індексу запит використовував стадію COLLSCAN (сканування всієї колекції), що відображається у полі stage. Крім того, сортування відбувалося в пам'яті (SORT). Після створення індексу стадія змінилася на IXSCAN (сканування індексу), а кількість переглянутих документів (totalDocsExamined) значно зменшилася. Сортування тепер відбувається автоматично завдяки індексу (без стадії SORT), що робить запит набагато швидшим.

2. Як зрозуміти, що індекс використовується? Наведіть скріншот або значення полів із explain(), які це підтверджують.
Щоб переконатися, що MongoDB використовує індекс для пошуку, потрібно проаналізувати результат виконання команди explain("executionStats"). Головним підтвердженням є зміна значень у полях stage та зменшення кількості переглянутих документів.
Ось ключові поля, які це підтверджують:
* Поле stage (Стадія виконання)
До створення індексу: Значення поля stage дорівнює COLLSCAN. Це означає повне сканування колекції — база даних змушена перебрати кожен документ у базі (усі 114 000 треків), щоб знайти збіги. Крім того, може бути присутня стадія SORT, що означає ресурсоємне сортування результатів у пам'яті.
Після створення індексу: Значення поля stage змінюється на IXSCAN (Index Scan). Це прямий доказ того, що база використовує побудоване "дерево індексу" для миттєвого знаходження потрібних записів.

* Поле keyPattern (або indexName)
Якщо стадія — IXSCAN, то всередині блоку inputStage з'являється поле keyPattern (або indexName), де чітко вказано, який саме індекс було застосовано (наприклад, { track_genre: 1, popularity: -1, "audio_features.danceability": 1 }).

* Поле totalDocsExamined (Кількість переглянутих документів) — якщо використовувався режим executionStats
До індексу: Це число дорівнюватиме загальній кількості документів у колекції (наприклад, 113999), оскільки база перевіряє кожен трек.
Після індексу: Це число різко падає і дорівнює лише тій кількості документів, які реально відповідають умовам запиту (наприклад, кілька сотень або тисяч).

3. Чи є запит покривним (covered query)? db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });
Ні, цей запит не є покривним.
Щоб запит був покривним, індекс має містити усі поля, які використовуються у фільтрі запиту, І усі поля, які повертаються у результаті.
Оскільки у нашому запиті немає проєкції (наприклад, { track_genre: 1, popularity: 1, _id: 0 }), MongoDB повертає весь документ цілком (у тому числі _id, artists тощо). Тому база даних все одно змушена звертатися до диска (стадія FETCH), щоб дістати інші поля документа, яких немає у створеному індексі.
